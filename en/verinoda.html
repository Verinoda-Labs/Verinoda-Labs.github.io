Developer tool

Verinoda

Gives coding agents a map of your code they can actually use. Every answer is a claim, with a status and the exact file:line it rests on.

CLI + MCP server · Apache-2.0 · 0.5.0 (beta)

Install

It looks at a repository as a running system.

Code, call and data flow, tests, configuration, git history and decision records. Questions in English or Turkish come back as claims with evidence. When a claim can't be supported, it says unknown and names the next check to run.

The journey of a question

The outputs below are real Verinoda output. In five steps a question becomes an answer with evidence.

  2. Question

    You ask in plain words.

    From the command line, or from a coding agent such as Claude Code or Codex; in English or Turkish.

  3. Index

    The repository is indexed on your machine.

    Indexing uses the AST and no LLM. What is in which file is worked out on your machine.

  4. Claims

    The answer is made of claims.

    Each claim points to a file and a line. You can open the line and read it yourself.

  5. Status

    Every claim has a status.

    “Verified” is never mixed up with “probably”. Next to each uncertain line, the reason is written.

  6. Decision

    What to do is your decision.

    The tool does not recommend. It brings what the code says and the questions it needs from you.

The status scale

Every claim carries one of these statuses. The first four may be presented as fact; the rest may not.

Presented as fact

  • statically_verifiedThe cited lines were checked again against the tree.
  • primary_source_verifiedConfirmed by a primary source such as pinned docs or git history.
  • observedObserved.
  • experiment_verifiedConfirmed by a recorded run.

Inference: not fact

  • strong_inferenceProbably. The reason is written next to it.
  • weak_inferencePossibly. Never presented as fact.

Everything else

  • contradictedFalse. The refuting evidence is shown.
  • staleThe code changed; the claim has to be verified again.
  • unknownWe do not know. The next step is stated.

What it checks for your agent.

  • Claims with evidence

    Each claim carries a status (statically_verified, strong_inference, unknown, stale) and the exact file:line or commit it rests on.

  • Name check

    Catches invented APIs in Python, Java, Kotlin and TypeScript imports, with the nearest real name.

  • Change review

    For a diff: changed definitions, who depends on them, findings by concern and which tests reach the change.

  • Documents and images

    PDF, Word, Excel and PowerPoint files become graph nodes and evidence that can be checked again.

  • Decisions stay human

    “Which one should we use” questions return a brief and open questions, never a recommendation.

  • Notes and 3D graph

    verinoda ui opens a local notes and graph view that follows the index as you edit.

Dedicated validators for game modding

For Minecraft datapack and mod projects, it also ships tools that catch the errors a compiler does not see.

  • datapack: tags that are checked but never added, objectives and scores used but not declared, calls to missing functions
  • mixin-check and access-check: Mixin targets and access widener entries are checked against compiled classes
  • shader: GLSL uniform blocks are compared with the Java code that fills them
  • lang: translation keys that are missing, written twice or used nowhere
